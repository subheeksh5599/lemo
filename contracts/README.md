# LEMO on-chain layer

Contracts and tests for the half of LEMO that has to live on chain: a Solidity
verifier for Substrate state proofs, the canonical title commitment, and two gated
representations that refuse to move without a finalized proof of the native face.

**Nothing here is deployed. No contract in this repository exists on Portaldot
Test, on Portaldot Live, or on any other chain. No transaction of any kind has
been sent by this workstream, and no key was used. The numbers, addresses and
roots quoted below are either read from a public node or computed by a test.**

## What is proven, and what is only designed

| Piece | State |
| --- | --- |
| sp-trie proof verifier in Solidity | works, verified against a live 4 node Portaldot V3 proof |
| blake2b-256 in Solidity (tests) | works, matches Python `hashlib` and the live chain precompile |
| blake2b-256 in production | adapter written for the Revive System precompile, selector confirmed by a live `eth_call`, never run from a contract |
| Title commitment and revision rule | works, pinned to a shared vector file |
| Gated ERC-20 / ERC-721 | works against a real proof and against a mock, in tests only |
| Root feed | design only, single attester, the whole trust model is in one EOA |
| Native registry (the thing being proven) | does not exist. The native record layout in this repository is a specification, not a chain fact |

## Architecture

```
        native face (does not exist yet)          EVM face (this repository)
        -------------------------------          --------------------------
        title record, 320 bytes                  SubstrateTrieVerifier
        storage key under a pallet map    <----  walks the trie from a state root
        committed in the state trie               decodes the record, checks bindings
                                                       |
        finalized block state root  ------>  RootFeed (attester publishes it)
                                                       |
                                                 Gate checks (revision, title,
                                                 token, operation, root, backing,
                                                 identity, nullifier)
                                                       |
                                          TitleGateERC20 / TitleGateERC721
                                          only then does state change
```

### The trie verifier

It decodes the layout sp-trie writes: leaf `0x40..0x7f`, branch `0x80..0xbf`,
branch with value `0xc0..0xff` (each with a 6 bit partial count), hashed leaf
`0x20..0x3f` (5 bits), hashed branch `0x10..0x1f` (4 bits), empty `0x00`. The count
field holds the count itself, and an all-ones field means continuation bytes
follow. Partial keys are packed two nibbles per byte with the padding nibble at the
**front** for an odd count. Values and child references are SCALE compact length
prefixed, a reference of exactly 32 bytes is a hash of another node and anything
shorter is inline, and a branch writes its value **before** its children in
ascending nibble order.

That last ordering is the one bug the audit found in this repository's server side
decoder (children read before value). `test/SubstrateTrieVerifier.t.sol` encodes the
same branch both ways and asserts that the children-first encoding does not decode
to the value that was written, so this verifier cannot quietly inherit that reading.

Statuses, and why a missing node is never an absence:

| Status | Meaning |
| --- | --- |
| `PROVEN` | the walk reached a value committed by the root |
| `ABSENT` | the walk proved the key is not in the trie: a committed branch has no child on the key's nibble, or a committed partial key diverges |
| `INCOMPLETE` | a node the parent references is not in the proof set |
| `INVALID` | a node does not decode, is padded, has a non-zero padding nibble, or forms a cycle |
| `ROOT_MISMATCH` | no supplied node hashes to the state root |
| `VALUE_MISMATCH` | a value was proven but it is not the value the caller claimed |

`ABSENT` is the only status that may ever be read as "the title is gone", and no
gate in this repository acts on absence at all. A truncated proof, a proof for some
other key, and a substituted node all land on `INCOMPLETE` or `INVALID`; none of
them can produce `ABSENT` or `PROVEN`.

One limitation, stated rather than hidden: a node whose bytes were substituted is
indistinguishable from a node that was left out, because in both cases the parent's
32 byte reference resolves to nothing in the set. Both are refusals. Telling them
apart would need the node set to carry a claim about nodes it does not contain.

### The commitment

```
commitment = keccak256(abi.encode(
  keccak256("LEMO.TITLE.COMMITMENT"),   // domain
  1,                                    // version
  titleId, chainId, nativeAsset, backing, owner,
  identityHash, vestingHash, permissionsHash, evmContract, revision))
```

Domain and version are both inside the preimage, so a record cannot be replayed
into another protocol or another schema revision. Absence is a value rather than a
missing field: `identityHash == 0` is a cleared identity, `backing == 0` is an
unbound backing, `evmContract == 0` is no representation. That is what lets the gate
refuse on a record it could decode.

`shared/title-vectors.json` holds four vectors (base, identity cleared, revision
bumped, backing unbound) with digests produced by `cast abi-encode` plus
`cast keccak`, independently of the Solidity code. `test/LemoTitle.t.sol` reads the
same file, so the vector file and the contract cannot drift.

The revision rule lives in `LemoTitle.commit`: a first commit must be revision 1,
every later commit must be exactly previous + 1, and title id and chain id are
immutable once set.

### The gate

A gated call must satisfy all of these before a single storage write:

1. root: `proof.stateRoot == feed.currentRoot()`, and the feed must hold a root at all
2. chain: `proof.chainId` and the decoded record's chain id equal the chain the token was deployed on
3. operation: the proof's operation equals what the call is about to do
4. token: `proof.token` equals this contract, and the decoded record's `evmContract` equals this contract
5. title: `proof.titleId` equals this token's title id
6. revision: the decoded record's revision equals the claimed revision, and is not below the last accepted one
7. record: the decoded record hashes to the commitment this token is anchored on, has a non-zero identity, and has non-zero backing

Then a nullifier `keccak256(titleId, revision, operation, stateRoot, token)` is
consumed, so the same proof cannot authorise a second state change.

Deliberate consequences of that nullifier scope, which a reviewer should weigh:

- one gated transfer per (title, revision, operation, root). A second transfer needs
  a newer revision or a newer root. That is what "block replay" implies at this
  granularity, and it is not a usable token design on its own; a real deployment
  would put a per-account nonce in the proof and key the nullifier on it.
- the anchor commitment has to be advanced by the owner when the native record moves
  to a new revision. Advancing it cannot fabricate a record: the new value must still
  hash to a record decoded out of a trie proof under the feed's root.

`approve` is not gated (it moves nothing); `transferFrom` is, and needs its own
proof. `safeTransferFrom` delegates to the same gate.

### The root feed and the trust model

`RootFeed` holds one root published by one attester. `ThresholdRootFeed` holds the
same root only after a fixed M-of-N set of attesters submits the same
`(root, blockNumber)` pair, and refuses an older block or a duplicate vote. The
trie walk, the record decode, the commitment and the nullifier are trustless
**given** that root. The root itself is not:

- the attester can publish any root, including one from a block that is not final,
  from a fork, or from nothing at all;
- the attester can publish an older root, which is how a proof consumed once could
  in principle become usable again with a different nullifier scope;
- the owner can replace the attester at any time.

`scripts/attest-root.sh` reads `chain_getFinalizedHead` and `chain_getHeader`
from every endpoint in `NATIVE_RPCS`, refuses unless they all return the same
root and block, and then sends `attest(root, block)` from one attester. Run it on
each signer of a `ThresholdRootFeed`; the quorum moves the root, not one key.

Pinned mode fixes one root forever and refuses every later attestation, including
an unpin (there is no unpin). A pinned feed is a one shot deployment: the pinned
block is the last state anything can prove. For a demo that is the strongest honest
setting available, because an EVM contract cannot see the native chain's headers and
therefore cannot check finality itself.

What this means for LEMO's two rules:

- Rule 1 (an EVM transfer reverts unless a finalized native proof holds) is enforced
  exactly as far as the root. If the attester lies, the gate enforces a lie.
- Rule 2 (native unbonding reverts while a representation is outstanding) is
  enforced by `UnbondGuard.requestUnbond` against `representationOutstanding()`. The
  native runtime would still have to call it, and that call does not exist yet.

### The Revive hash precompile

Production hashing goes through `ReviveBlake2b256`, which calls the pallet-revive
System precompile at `0x0000000000000000000000000000000000000900`:

```
function hashBlake256(bytes input) external view returns (bytes32);
selector 0xc7dff686
```

Confirmed against the live test endpoint, not from documentation:

```
eth_call {"to": "0x...0900", "data": "0xc7dff686" ++ abi.encode(bytes("abc"))}
  -> 0xbddd813c634239723171ef3fee98579b94964e3bb1cb3e427262c8c068d52319
control, same address with the selector of hash(bytes) (0xaa1e84de)
  -> revert "panic: memory allocation error", i.e. that selector is not implemented
```

`0xbddd813c...` is BLAKE2b-256("abc"), and the same input hashes to the same value
in `test/harness/Blake2b256.sol` and in Python's `hashlib.blake2b(digest_size=32)`.
`cast sig "hashBlake256(bytes)"` prints `0xc7dff686`.

The adapter reverts when the call fails or returns anything but 32 bytes, so a
chain without the precompile (any local EVM, any fork) fails closed instead of
returning zero.

### Compile target

`foundry.toml` pins solc 0.8.26, the optimizer at 200 runs, and
`evm_version = "shanghai"`. Revive's interpreter rejects Cancun opcodes; a
constructor that emits one reverts with empty data inside `eth_estimateGas`, which
is one of the most expensive mistakes to diagnose from the outside. Metadata and
the CBOR hash are off so the bytecode is reproducible.

Code size is also a cost on this chain: the runtime charges a refundable
`depositPerByte` (about 0.06 POT per byte on V3 Test), so a gated token plus
verifier is a real bill. `script/Deploy.s.sol` deploys four contracts and has never
been run; budget it before asking anyone for funds.

## Commands

From the repository root, with Foundry on `PATH` (`export PATH="$HOME/.foundry/bin:$PATH"`):

```bash
forge build                 # compiles contracts/ and test/
forge test                  # the whole suite
forge test -vv              # what the report below quotes
forge test --match-path test/SubstrateTrieVerifier.t.sol -vv
forge fmt --check           # formatting
```

Refusals worth running by hand:

```bash
# the deploy script refuses to do anything without an explicit confirmation
forge script script/Deploy.s.sol -vv
#   [Revert] refusing to deploy: set DEPLOY_CONFIRM=yes

# regenerate the synthetic trie fixtures (only needed if you edit the generator)
python3 test/tools/gen_trie_cases.py

# refresh the live proof fixture (network, read only)
curl -s -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"state_getReadProof","params":[["0x26aa394eea5630e07c48ae0c9558cef702a5c1b19ab7a04f536c519aca4983ac"],"0x56e60dd2c4ac9f228925367d0d94b238f8136d7f57d2ccaff23b9947ac590e41"]}' \
  https://test-node-v3.portaldot.dev
```

Running `forge install` again is not needed: `forge-std` is vendored under
`test/lib/` so that another agent's `lib/` is untouched.

## Known issues and open questions

1. **The native registry does not exist.** The 320 byte record and the storage key
   derivation (`keccak256("LEMO.NATIVE.TITLE", titleId)`) are this repository's
   specification. A real native map would key on
   `twox128(pallet) ++ twox128(item) ++ map hasher(titleId)`. The verifier takes the
   key as an input and does not care, but nothing proves a record the chain does not
   have.
2. **One gated transfer per revision per root.** See the nullifier note above. This
   is the literal reading of "nullifier per (titleId, revision, operation, root)" and
   it is not sufficient for a production token.
3. **The root is one signature.** Finality is asserted, not proven. Pinning narrows
   it to one block and one decision.
4. **A pinned feed is terminal.** There is no unpin by design; a mistaken pin needs a
   redeployment.
5. **Substituted and missing nodes are indistinguishable** at the verifier's layer.
   Both refuse; neither can produce `PROVEN` or `ABSENT`.
6. **The production hash path has never run inside a contract.** The precompile was
   confirmed by `eth_call`; the adapter's own `staticcall` wiring is only exercised
   by code inspection, because Foundry's EVM does not implement pallet-revive
   precompiles and a fork copies state, not precompiles.
7. **No fuzzing or invariant campaign yet.** The suite is example based, with 64 fuzz
   runs configured for anything that uses `vm.assume`. The nullifier and revision
   invariants are the obvious next candidates.
